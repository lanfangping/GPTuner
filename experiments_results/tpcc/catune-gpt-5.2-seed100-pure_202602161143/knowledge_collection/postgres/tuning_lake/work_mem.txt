If it’s too low, queries spill to temp files and slow down; if it’s too high, many concurrent operations can consume large amounts of RAM and destabilize throughput. Size it by estimating worst-case concurrency: total potential memory can reach roughly `N * work_mem` across concurrent operations/sessions, and hash tables may use up to `work_mem * hash_mem_multiplier`. To choose a starting value, estimate active sessions and the number of memory-using operations per query (a small single-digit number, often ~2–5 for sorts/hash joins), and target `work_mem ≈ (0.25–0.50 * RAM) / (active_sessions * consumers_per_query)`, then adjust based on observed memory pressure and query behavior.
