{'suggestion': 'Treat `work_mem` as a per-operation (sort/hash) memory cap (default 4MB; kB if no unit) that, when exceeded, causes spills to temporary disk. Because a single query/session can run multiple memory-hungry operations concurrently—and hash tables can grow up to `work_mem × hash_mem_multiplier`—total RAM usage can be many times `work_mem`. Choose a value by estimating concurrency so that (active sessions) × (concurrent sorts/hashes per session) × (`work_mem`) fits comfortably in available RAM, then tune based on observed temp-file spills vs. memory pressure. In practice, start with a modest increase from the 4MB default (often around 16MB for many systems; low MBs for OLTP, potentially much higher for OLAP with few concurrent queries) and adjust upward carefully to avoid destabilizing throughput under high concurrency.'}
