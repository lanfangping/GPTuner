For PostgreSQL’s (autovacuum) **`autovacuum_vacuum_cost_limit`** behavior on a per-table basis, set **`autovacuum_vacuum_cost_limit`** (sometimes referred to in tuning guides as “commit siblings” in the sense of concurrent/autovacuum resource sharing) so that **a single autovacuum worker can make steady progress without starving foreground queries**—as a concrete starting point use **`autovacuum_vacuum_cost_limit = 2000`** (up from the default **200**) on busy systems, and if you run **N** concurrent autovacuum workers, scale roughly as **~(2000 ÷ N)** per worker (e.g., **N=4 → ~500**, **N=8 → ~250**) while monitoring latency and vacuum progress.
